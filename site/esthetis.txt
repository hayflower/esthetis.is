03  SELECTED WORK
------------------------------------------------------------------------

Client names and identifying details are withheld under NDA.

Migrations and handovers
  A payments startup ran its production system on AWS. Working alongside
  their two developers, I migrated it to self-managed servers. Hosting
  costs came down by roughly half, and the team took over the new setup
  with backups in place and documentation for running it.

  On another engagement I took over systems that had been built and run
  without documentation, worked out what they did and how they fit
  together, and left the client with runbooks and architecture documents
  for all of it.

MFA and device management for an eight-person team
  An eight-person team needed MFA and managed devices. I rolled out MFA
  through Entra ID, enrolled their devices in Intune and moved shared
  credentials into Bitwarden. The team ended up with MFA in place and
  shared passwords kept in one managed vault.

Silent fallback in key generation
  During a security review, I traced the client's key generation path
  and found that keys created in production were not coming from a
  cryptographically secure source. The entropy module tested for a
  secure random API once, at load time, and if it was missing fell back
  without warning to the runtime's general-purpose generator. A refactor
  had moved the import of the shim that provides that API below the
  entropy module, so in affected builds the check always ran first and
  every key took the fallback.

  That generator isn't built for cryptography and its internal state can
  be recovered from its output, so every key from those builds had to be
  treated as guessable. I recommended removing the fallback so key
  generation fails closed, adding a startup self-test and a build-time
  check on import order, and forcing rotation of affected keys, with
  affected users contacted directly before any public statement. The
  client implemented the fixes.

04  NOTES
------------------------------------------------------------------------

PHP2Shell response, October 2026
  PHP released fixes for CVE-2026-109618 and CVE-2026-109619
  ("PHP2Shell"), two remote code execution flaws in PHP itself, on 21
  October 2026. Exploitation attempts were being reported the same day.
  I started work about nine hours after disclosure on a client site
  running an affected PHP 8.3 release under PHP-FPM.

  I put up a maintenance page, upgraded to PHP 8.3.36, restarted
  services and restored the site. I also disabled session upload
  progress, as PHP recommends until the related CVE-2026-115560 is fixed
  in its next regular release, and tightened the request body limit at
  the web server.

  To verify the fix, I confirmed the running version from both the CLI
  and FPM, checked that the package changelog listed both CVEs,
  confirmed the new setting was active, and tested login, booking and
  checkout end to end.

  To check for compromise, I reviewed web and PHP logs back to the first
  reported in-the-wild attempts. A small number of oversized multipart
  requests appeared in the days around disclosure. All were rejected or
  failed, and none were followed by unusual activity from the same
  sources. CMS core and plugin checksums were clean, no PHP files had
  been added or changed in the web root, and crontabs, admin accounts
  and outbound connections showed nothing unusual. No signs of
  compromise were found.

  Total downtime was about 15 minutes. No action was required from the
  client.
